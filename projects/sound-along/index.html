Who did what

Where people and agents worked

Alex set the goal and the standard, ruled between the options built for him, required two checkers before anything went public, set the budgets and stop points, and approved anything public or deployed. AI agents wrote and checked the code and documents under those rules, and one main Claude session coordinated them, merged their work and measured the results. The record shows his direction, rulings and reviews; it shows no hand-written code.

Below that night, the same pattern ran unattended: each overnight lane loops like this.

Coordinating Claude

Turns a goal into short briefs, launches lanes, merges, reruns the checks itself, and reports the numbers. It keeps a running log and a status file so the next session can pick up.

Builders

Mostly Codex's Sol, plus Sonnet agents, each in its own branch and copy of the code, so many can work at once without collisions. Up to nine ran at once.

Checkers and reviewers

One capable checker from a different model family than the builder where possible, for each piece of work. Panels of several judges only when scoring or comparing, like ideas or versions of a script.

Alex

Sets the goal and the standard, rules on choices from options built for him, and listens to and clicks through results. He also sets budgets and stop points, and approves anything public or deployed.

Other vendors

Running agents from other companies

Most builders and reviewers were OpenAI's models through the Codex command line: Sol for building and checking, Astra for planning, reviewing and editing. Claude wrote a small driver script for each run that starts them, waits, and collects their replies. Panels for ideas and scoring also drew on other model families, including Google's Gemma and Alibaba's Qwen.

How they search the web

  • Codex agents use Codex's own web search, switched on per call (a setting on the command), and write their findings into their lane folder with links to every source.
  • The coordinator uses a separate search service, Tavily, plus the built-in browser, to spot-check what the agents found. The Tavily helper couldn't run inside Codex's sandbox, so the two stay split.
  • Every research lane gets a checker from a different model family, reading the same sources, and research always goes back to primary sources rather than summaries.

Context

Where it comes from

  • Files, not chat. Other vendors' agents never see the conversation. Everything they need is written down.
  • A shared floor, AGENTS.md, holds the rules every tool reads: environment, standards, what never to touch.
  • A shared brief per job sets audience, tone and the truth bar. A short task brief points at it and at exact sources.
  • Live rulings are added to the brief file mid-run, and the next agent call reads them.
Writing

Rules for files

  • Reviewers write nothing. Their reply is captured to a report file.
  • Builders write only in their lane: a separate folder or git worktree, enforced by the sandbox.
  • No network, no deploys, no browser inside a lane. The driver renders, tests and commits.
  • Shared files like the test runner are off limits. Builders name new tests, and the coordinator registers them.
  • Every reply ends with what was built, how it was checked, and what couldn't be verified.
Guards

What's always off limits

  • Confidential event files are never opened or sent to any model.
  • No personal data, keys or private addresses in anything public.
  • Work is labeled as a suggestion until Alex rules.
  • Failures are loud: a failed call is logged and retried once, never silently dropped.
Varying perspectives

Orthogonal fan-outs

A plain fan-out splits work into pieces. An orthogonal fan-out sends the same question to agents set up to see it differently, so their blind spots don't overlap. Each agent is changed along one or two axes, and the differences between their answers are treated as the useful part.

How the axes are used

  • Role gives each agent a person to be, with that person's worries: a judge wants proof, a teacher wants respect for how reading works, a speech coach wants lines that can be said in one breath.
  • Lens narrows what it looks at, so two reviewers of the same page don't repeat each other.
  • Altitude separates "is this the right thing?" from "is this thing right?"
  • Stance pairs a critic with a growth reviewer: one looks for what breaks, one for what it could become.
  • Model family matters most when scoring or judging. Models from one company tend to share blind spots, so their agreement says less.
  • Context is the cheapest test of clarity: a reader with no background shows what a judge hearing it once will miss.

A three-agent recipe

SharedOne question and one set of sources, the same for everyone: "Review this script for tomorrow's judges. Sources: the deck, the code, ReadWorks' brief."
Agent 1: role and stance"You are a skeptical AWS judge. Find what you wouldn't believe."
Agent 2: role and lens"You are a reading teacher. Is it true to how children learn to read, and does anything oversell?"
Agent 3: context"Read only this file, with no other background. What does it do, and what will you remember?"
MergeOne editor reads all three, fixes every factual problem, takes other changes only for a real gain, and lists what was rejected and why.

Prompting style

How Alex prompts

Typical prompts during the event were one short line. A few long prompts, which read like spoken dictation, carried the thinking. About a fifth were short replies to a set of options, like "build both" or "start it".

Lead with purpose and audience

States what the work is for and who will see it before asking for it.

This is for a teammate building the pitch, so put the key ideas first.

Name the agents and the split

Says which kind of agent, how many, and what each looks at.

Run two deep reviewers, one on content and one on presentation.

Set guard rails in plain words

Says what's off limits and what must be checked before anything leaves.

Everything goes public, so run two checkers before each post.

Ask for options, then rule

Asks for the real questions with a few options for each, then picks with a word or two.

What should we loop on tonight? Give me options, then I'll pick.

Correct fast, in both directions

Short corrections, sometimes swinging back the other way on the next try until it lands.

Too detailed. Concept first. Now there isn't enough detail.

Set the standard, not the wording

States the bar for truth and tone, then lets agents find the words.

Be persuasive, but it has to stay true. Close enough is fine; false never is.

Report symptoms, not fixes

Describes what he heard or saw and leaves the diagnosis to the agents.

The volume seemed to fade in and out.

Budget and stop points up front

Sets a reserve of usage, deadlines and when to stop, and asks for questions before he goes away.

Keep a usage reserve for the morning, and ask questions before I step away.

Long messages read like dictation sent without editing, so they think out loud. Agents are asked to check for misheard words rather than take them literally.

Habits that held it together

Methods

  • Briefs with a fixed shape. Every agent gets the goal, what done means, the rules, its own lane, and a closing note saying what it built, how it checked it, and what it couldn't verify.
  • Measure before claiming. Each change carries a before and after number from a script, and the coordinator reruns the lanes' claims itself.
  • Guards versus behavior checks. Tests that protect mechanics can block a merge. Tests that only describe today's undecided design just report, so nothing gets locked in by accident.
  • Labels for who decided. Agent work is marked as a suggestion until Alex rules on it, so drafts never pass for decisions.
  • Prototype several ways. Looks, voices and panels were built as working options for the team to choose from.
  • Review pages instead of long chat. Maps, option sets and plans went on private web pages so Alex and the team could react and decide.
  • Freeze before the demo. A feature freeze the afternoon before, then only the spec, video and pitch.
What we learned

Lessons from the record

  • People reviewing is the real limit. One night's nine features took agents about 20 minutes, against an estimate of 20 to 37 hours of human work. Deciding and checking took the time.
  • Too many fact-checkers flatten a pitch. Six review rounds made the script more accurate and less persuasive. A correction round restored it under a simple rule: claim things at their true size.
  • Check a check. Reviewers sometimes judged an old version or the wrong file. The coordinator confirmed key findings before acting on them.
  • Test the whole path early. A stand-in voice ran the full re-narration tool overnight and found three problems before the real recording.
